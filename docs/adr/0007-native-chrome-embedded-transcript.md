# The phone is native chrome around an embedded transcript

The phone client began as `mobile.html` — the desktop renderer with a touch layout — first as a home-screen web app and then wrapped in a one-view WKWebView shell. It got every feature the desktop got, the day it got it, which is the whole reason it existed. It also never stopped feeling like a web page: rows that are `div`s, a back stack mirrored into `history.pushState` so the browser's edge swipe would do something, sheets drawn by CSS, a header whose height is arithmetic against the keyboard and three documented workarounds for what the keyboard does to `dvh`. Every one of those is chrome, and chrome is exactly what iOS does well and a web page does badly.

The transcript is the opposite case. Streaming markdown with the paced reveal, Mermaid and KaTeX, tool-call cards, file-change cards, plan cards, the question dock, approvals, the review screen, forking, queued follow-ups — that is where the product's surface area lives, and it changes weekly. A native transcript would have to reimplement all of it against the bridge and then keep two implementations in step in a single-user project. And it would render in the same WebKit either way; there is no fidelity to win.

So the seam is drawn there. SwiftUI owns pairing, the chat list, navigation, new chat, row actions, settings, and notifications, talking to the host over the existing WebSocket bridge with hand-written Codable models pinned by fixture tests. One warm `WKWebView` loads `mobile.html?embed=1` once and is pushed as a destination; the page switches sessions in place on `openSession(id)`, so opening a chat is a native push onto a view that is already painted, and the shell never shows a loading state the renderer would have had to hide. The two sides speak a small typed contract (`src/renderer/mobile/nativeHost.ts`, mirrored in Swift) — title and attention out, theme and session in — rather than sharing state.

Notifications follow the same rule: they are chrome. The host sends APNs directly, token-authenticated with a key that lives on the Mac, because a push that travels Mac → Apple → phone has the same trust shape as the bridge itself, and the ntfy relay it replaces was a third party that saw prompt text. ntfy stays as an alternate sink for anyone without a paid developer account.

The alternative worth naming is finishing the web app's polish instead — every rough edge here was fixable in CSS and a day of work, and the last two were. What that cannot fix is that the *feel* of scrolling a list, pulling to refresh, swiping a row, and pushing a screen is the platform's, and a web page can only approximate it. The other alternative, a fully native client, buys widgets and Live Activities nobody asked for at the price of a second transcript. Neither moves the seam; both are why it sits where it does.

What this costs: two model definitions (Rust and Swift) that can drift — held by decoding captured real payloads in tests and by tolerant decoding, so an added field never breaks the phone — and the keyboard inside the transcript is still WebKit's, though the container that owns the safe areas is now native, which removes the standalone-web-app class of viewport bugs.
