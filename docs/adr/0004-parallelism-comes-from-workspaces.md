# Parallelism comes from workspaces, not from sessions per workspace

Running several agents against one repository at the same time — including the same branch and the same checkout — is the point of the app. That concurrency is expressed by creating several workspaces, each holding exactly one session. Nothing stops two workspaces from naming the same `path`: there is no unique index on `workspaces(project_id, path)`, `create_current` mints a fresh row on every call, and the filesystem watcher deduplicates by canonical checkout path precisely so that many workspaces over one checkout cost a single OS watch.

The alternative — letting a workspace hold many sessions — is the shape someone will reach for on first contact with the one-session rule, because "workspace" sounds like a directory and the rule then reads as "one agent per directory." It is not that. A workspace is a unit of assigned work, and it is the identity behind a sidebar row, a task label, an attention marker, and an archive lifecycle. Splitting one row across several sessions makes every one of those ambiguous — which session's attention does the row show, and what does archiving it mean — for no gain in what can actually run at once.

The rule therefore stands, with one known violation: the CI check-failure follow-up launches into the existing `workspace_id`, so its new session displaces the original in the renderer's `workspace → session` lookup, which resolves by most recent activity. That is a defect in the follow-up path, not evidence for the other model, and the fix is to give it its own workspace the way `fork_session` does.
