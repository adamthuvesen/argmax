# Agent tools are one MCP server, not five integrations

Argmax already had a control plane before it had tools. `session_control.rs` runs a private Unix socket for the lifetime of an app run, mints a bearer token per session, and injects the socket path, the token, and `ARGMAX_BIN` into every child it spawns; `argmax session launch|move|list|message` speaks that socket from the command line. The five provider CLIs, meanwhile, agree on almost nothing except MCP over stdio — it is the one extension mechanism all of them, and the ACP spec, guarantee. So the tools are a second face on the existing socket rather than a second control plane: `argmax mcp` is a subcommand of the same binary, it holds no state, and every tool call serialises the same `SessionControlAction` the CLI builds and gets back the same `SessionControlResponse`. Adding a tool means adding a variant to that enum. A sidecar process, an HTTP transport, and a per-provider integration were all considered and none of them buys anything the socket does not already have.

What differs per provider is only how one server spec reaches one run, and [mcp_injection.rs](../../src-tauri/src/providers/mcp_injection.rs) is the single place that knows: `--mcp-config` for Claude, `-c mcp_servers.argmax.*` for Codex, an `mcpServers` entry in `session/new` and `session/load` for Cursor's warm ACP pool, `OPENCODE_CONFIG_CONTENT` for OpenCode, and a config file in the checkout for Grok and for Cursor's one-shot path, which have no per-launch flag at all. None of these replace the user's own servers: `--strict-mcp-config` is deliberately not passed, OpenCode's inline config is merged over the global one, and a `.cursor/mcp.json` the user keeps is parsed and rewritten with one key added rather than overwritten. Where the spec is per-launch the token rides in the spec's own `env`, which is what lets a warm shared process hand each session a different credential.

Safety is caps and visibility, not dialogs, because auto-approve is the app's default permission mode and a new approval prompt would only be clicked through. A launch is a top-level session in the sidebar, visible and spending real tokens, so the guards are the ones that keep a chain finite: depth at most two, ten launches per session, no self-messaging, both counted from the database rather than from anything the agent controls. A tab an agent opens belongs to that session and appears in that session's own pane, so browsing is watched work; a session can only drive tabs it opened. Messaging is queue-until-idle plus a blocking `session_wait`, because no CLI surfaces a server push into a running model — a running agent sees a message when it asks for one or when its turn ends, and the tool descriptions say so.

Three costs are accepted. The per-session token appears in `ps` for Claude and Codex, whose spec rides argv; that is the same exposure the environment variable already had to a same-user process on a single-user local machine. Grok and Cursor's PTY path need a file written into a checkout Argmax does not own, so each is added to that checkout's `info/exclude` before it is written and removed again when the child exits — a launch must never make the user's own repository look dirty. And Grok gates repo-local MCP servers on folder trust, so a launch also records the workspace in `~/.grok/trusted_folders.toml` exactly as Grok does when the user answers its prompt, holds it only while the launch runs, and never removes an entry it did not write.

The file-based paths carry one more constraint that shapes them. [ADR 0004](0004-parallelism-comes-from-workspaces.md) makes several sessions over one checkout the normal case, and one checkout is one config file — so neither file may hold anything one session can overwrite for another, and a share in the file's lifetime is ref-counted rather than owned by whichever launch finishes first. How each file avoids holding a credential was measured rather than assumed, and the two CLIs differ. Grok starts its MCP server with the environment its own process has, so its config carries no credential and every session writes identical bytes. Cursor sanitises that environment — the server reports `ENV_MISSING` — so its spec must carry the credential, and the entry is therefore named per session rather than shared. Naming every entry per session would have been the uniform choice, and it was rejected because it would leak a session id into the tool names the model reads on a provider that does not need it.
