# A multitask is a sibling session, not a second turn

Dispatching a second piece of work from a chat whose agent is already running looks like it wants a second turn in that session. It cannot be one. Five things in the runtime assume a session has at most one turn in flight: one provider handle per session, `is_current_provider_invocation` discarding output from any invocation that is not the current one, a single `sessions.state`, one workspace path, and one `provider_conversation_id`. A second concurrent turn would have to defeat all five, and the visible failure — two agents' output interleaved in one transcript under one state — is worse than the invariant it broke.

So a multitask is a sibling: a new session in a new workspace, with a fresh provider conversation, pointing by default at the same checkout the parent is working in. The parent's turn is untouched, which is the entire user-facing promise of the feature.

Sharing the checkout rather than forking a worktree is the cheaper half, not the compromised one. The person asking for it is mid-task on a branch and wants the fix *there*; a worktree would put it somewhere they then have to merge back. Because the multitask starts a fresh context instead of forking the parent's transcript, none of the fork machinery applies — no mid-turn `fork_session` guard, no `provider_conversation_id` collision — and it works on providers that cannot fork a resumed conversation at all. What it does inherit is the shared checkout's real hazard: two agents editing one tree. The prompt says so, and isolation stays one flag away.

The result comes back passively. A completion notice would deliver the multitask's answer to the parent as a turn, waking an idle agent and, worse, arriving as an interruption in the middle of the work the person did not want interrupted. Instead the finish writes a timeline row the chat draws as a launch row, and a `multitask`-kind inbox row that rides into the parent's *next* prompt as a preamble. The person is told immediately; the parent's agent is told when it next has a reason to listen.

The alternative worth naming is a queued follow-up, which the app already has: it is the right answer when the work belongs to this conversation and can wait. Multitask is for the work that belongs to neither — unrelated, and wanted now.

Being a sibling session is an implementation fact, not a thing the reader should have to hold. A multitask is presented as what it behaves like: work running alongside this turn. It has the shape of a subagent launch row in the transcript, it opens in the same dock the subagents open in, and it has no sidebar row of its own — a row there would say "another chat to keep track of", which is exactly the cost the feature exists to avoid. What it does keep, because it is a session, is the ordinary chat surface inside that dock tab, so it can be answered without being promoted to a chat of its own. The one place the sibling nature must surface is an orphan: with its launching chat gone there is no dock left to hold it, so its row comes back rather than leaving a checkout unreachable.
